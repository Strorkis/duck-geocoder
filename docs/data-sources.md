# データ源の調査

**権利面を先に確認し、使えるものだけ属性を測る**という順で進める。

もとは意味検索 (埋め込みによる類似検索) の材料を探す調査だった (2026-09-06)。
その後ドローン向けという方向が決まったので、**何が要るか**を先頭に置いた (2026-09-13)。

## 0. 何が要るか、どこから取るか

ドローンの運航を考えるうえで要る情報と、その出所。**用途ごとに要るものが違うので、
表にしてから取りに行く。**

| 要る情報 | 何に使うか | 出所 | 状況 |
| --- | --- | --- | --- |
| 地形 | 障害物・見通し | Mapterhorn (基盤地図情報) | **導入済み** |
| 行政区域 | 申請の宛先・逆ジオコーディング | Overture | **導入済み** |
| 建物の高さ | 障害物 | PLATEAU | 港区のみ。全国で**5〜10GB**の見当 ([pipeline.md](pipeline.md)) |
| 人口密度メッシュ | **SORAのGround Risk** | 国勢調査 地域メッシュ統計 ([e-Stat 統計GIS](https://www.e-stat.go.jp/gis)) | 未取得。**測量法の対象外** (下記) |
| DID (人口集中地区) | 航空法第132条の許可要否 | **令和2年国勢調査** (総務省統計局) | 未取得。**国土数値情報A16は平成27年止まりで使えない** |
| 道路・土地利用・用途地域 | Ground Riskの補強、緊急着陸地点 | PLATEAU (`tran`/`luse`/`urf`) | **300都市前後にある** |
| 樹木・鉄塔・煙突の高さ | 障害物 (3D) | 点群 | PLATEAUの `veg` は34都市、`cons` は5都市しかない |
| 送電線・鉄塔の高さ | 障害物 (3D) | **出所が無い** | 点群に分類が無く、点群自体も全国に無い。OSMは参考どまり。**空欄のまま置く** |
| 空港等の制限表面 | 空域 | 航空局告示 | GISデータは限定的。要調査 |
| 飛行計画・許可 (DIPS2.0) | — | — | **公開APIなし**。業務システムの領分 |

**線引き:** ここで扱うのは**静的な地理条件**まで。DIPS/SWIMのような動的・制度の層には
踏み込まない。

### 出所の格付け: 全国 × 公的なものを本線にする

判断に使う値は、**全国で同じ基準が引けて、公的な出所を持つもの**に限る。

| 格 | 例 | 扱い |
| --- | --- | --- |
| **本線** | 国勢調査 (総務省統計局)、国土数値情報、PLATEAU、基盤地図情報 | 判断の根拠にする |
| 参考 | OpenStreetMap、Overture | 補助表示。**判断の根拠にしない** |
| 参考 (地域限定) | 自治体の点群 | 検証や地域限定の表示 |

理由は2つ。**一部の地域でしか出ない答えは、運航の判断に使えない** こと。
そして安全に直結する値の出所は追跡できる必要があること。

いま使っているOverture (行政区域・建物) は**参考**の側にある。
逆ジオコーディングや地図表示には十分だが、**リスクの計算には使わない。**

行政区域は本来 国土数値情報 N03 に寄せたい。変換は実装済みだが、
**N03は複製に国土地理院長の承認が要る** (下の表) ので配信していない。
承認の申請は保留中なので、**当面は「承認が要らない全国データ」から埋める。**

### 地上リスクは人口密度だけにしない

SORAの iGRC は人口密度で決まるが、**それだけをリスク値にしない。**
実際の運航では「人がいるか」と別に「**落ちてはいけない場所か**」がある。

| 重ねたいもの | なぜ | 出所 |
| --- | --- | --- |
| 人口密度メッシュ | SORAのiGRCそのもの | 国勢調査 (e-Stat) |
| 道路 | 人と車がいる。墜落は二次事故になる | PLATEAU `tran` (302都市) / 国土数値情報 |
| 学校・病院などの施設 | 落ちてはいけない場所 | 国土数値情報 (P02など) |
| 危険物施設・プラント | 同上。被害が波及する | 国土数値情報 / OSM |
| 鉄道 | 同上 | PLATEAU `rwy` / OSM |
| 水部 | 逆に**リスクが低い**。着水は選択肢になる | PLATEAU `wtr` (57都市) / Overture |

**設計の方針: 出所ごとに「メッシュに載るリスク面」を作り、重ね合わせで最終値を出す。**
1つの式に固め打ちしない。理由は3つ:

- **規格と運用がずれる。** SORAのiGRCは規格の値で、そこに独自の係数を混ぜると
  「規格に沿った値」が出せなくなる。**人口密度だけの層は独立に持ち、
  他は加算レイヤーとして分ける**
- **要る層が用途で変わる。** 目視外か目視内か、機体の大きさ、昼夜で効く層が違う
- **データの整備範囲が層ごとに違う。** 道路は302都市、水部は57都市。
  「無い層は寄与ゼロ」で成立する形にしておかないと、範囲の広い地域で使えない

メッシュの粒度は、国勢調査の基準地域メッシュ (500m / 1km) に合わせるのが素直
(人口が最初から載っている)。

#### 人口メッシュは境界データを落とさなくてよい

**地域メッシュは経緯度から機械的に決まる方眼**で、測量成果ではない。3次メッシュ (約1km)
も、それを4分割した500mメッシュも、**メッシュコードから座標を計算で出せる**。

| | 取るもの | 測量法 |
| --- | --- | --- |
| 人口の値 | [e-Stat 統計GIS](https://www.e-stat.go.jp/gis) の地域メッシュ統計 | 対象外 (統計) |
| メッシュのジオメトリ | **自前で計算して作る** | **対象外** |

境界データのダウンロード自体が不要になるので、**測量法の懸念が原理的に発生しない**。
計算は決定的なのでRust側でテストも書ける (`pipeline/src/bin/` の流儀に合う)。

なお小地域 (町丁・字等) の境界データは測量成果に基づく図形を含むので扱いが違う。
**メッシュと混同しないこと。**

取得は [e-Stat API 3.0](https://www.e-stat.go.jp/api/) (バージョン3.0から小地域・
地域メッシュに対応) か、統計GISからの直接ダウンロード。**APIはユーザ登録して
アプリケーションIDを取る必要があり**、使った場合は次のクレジット表示が要る。

> このサービスは、政府統計総合窓口(e-Stat)のAPI機能を使用していますが、
> サービスの内容は国によって保証されたものではありません。

利用規約は**データ本体とAPI機能で別々**にあり、API側は短時間の大量アクセスを禁じている。

**建物以外の3D障害物は、当面あきらめる。** 点群がほぼ唯一の出所になるが、
その点群が全国に無く、送電線・鉄塔の分類も持っていない (下記)。
**全国で同じ判断ができないものは本線にしない**という格付けに従う。

つまり当面の3D障害物は **建物 (PLATEAU) と地形 (Mapterhorn) の2つ**。
どちらも導入済みで、広げる先も決まっている。

### 点群のオープンデータ (調査済み・2026-09)

**結論を先に。**

1. **権利面は問題にならない。** 主要な県はCC BY 4.0で、商用も含めて二次利用できる。
   むしろ地理院の方が厳しい (測量法の申請が要り、受注生産)。
2. **送電線・鉄塔として分類された点群は無い。** 期待していた
   ASPRS Class 14 (電力線) / 15 (鉄塔) は入っていない。公開データの分類は
   **地表面か否か (DSM / DEM) までしか無い**。フィルタ一発では取れない。
3. **Rangeで直接読む設計にはなっていない。** 図郭ごとのZIP (平均200〜300MB、
   最大5.6GB) で、中身は圧縮済みのLAS。PLATEAUのように「必要な所だけ引く」が効かない。
   **持つなら派生物にする**という方針は変わらない。
4. **そして全国には無い。** 県全域まで来ているのは数県。
   **この節の調査は「当面使わない」という結論に落ち着いた** (下記)。
   記録として残すのは、同じ調査を繰り返さないため。

#### 送電線・鉄塔が分類されていない理由

公開データの多くが **LAS 1.2** (レコードフォーマット2・3) で作られている。
ASPRSの標準分類でClass 14/15が**電力線・鉄塔に割り当てられたのは LAS 1.4
(レコードフォーマット6以降)** で、LAS 1.2では14も15も予約値でしかない。
**器が持てないものは入っていない。**

加えて、公共測量の作業規程が求める分類は数値標高モデルを作るためのもので、
地表面・建物・植生までしか分けない。地理院の点群も
[簡易分類 (地表・水部・その他)](https://www.gsi.go.jp/gazochosa/tengun.html) どまり。

#### 送電線・鉄塔は当面あきらめる

「位置はOSM (`power=tower`)、高さはその地点の点群の最高標高」という組み合わせは
技術的には成り立つ。**が、主軸にはしない** (2026-09-13の判断)。理由は2つ。

- **点群が全国に無い。** 上の表のとおり、県全域まで整備されているのは
  兵庫・山梨・長崎などに留まる。全国で同じ判断ができないものを、
  障害物判定の土台には置けない
- **OSMを使う以上どこまでも「参考」にしかならない。** 障害物の有無は
  安全に直結するので、出所は公的なものにしたい

**全国をカバーする公的な出所が現れるまで空欄のままにする。** 点群から鉄塔を
推定する (分類を自前でやる) のは研究の領分で、このリポジトリの仕事ではない。

点群そのものは、地域を限った参考表示や検証用としてなら使い道がある。
その場合もCOPCなどの派生物にしてから。

#### Range で引けるか

引けない前提で設計する。図郭ごとのZIPで、中のLASは圧縮されている。
`remote_zip` で中央ディレクトリから1エントリを取り出すことはできるが、
**deflate圧縮されていれば先頭から流すしかない**ので、200MBのファイルから
一部分だけ、とはいかない。

ブラウザから引くなら [COPC](https://copc.io/) (Cloud Optimized Point Cloud) が
Range前提の形式だが、**国内の公開データにCOPCは見当たらない**。
変換するのはこちら側の仕事になる。TB級の生データをそのまま配る話ではなく、
**必要な派生物 (障害物の高さなど) を作って配る**方向で変わらない。

### PLATEAU の配信カタログAPI

[`https://api.plateauview.mlit.go.jp/datacatalog/plateau-datasets`](https://api.plateauview.mlit.go.jp/datacatalog/plateau-datasets)
が**公式に**都市一覧とCityGML zipのURLを返す (`latest_citygml`、307都市)。

**配布ページのURLを組み立てて取りに行くのではない。** 公式APIがあるのでそれを使う、
という位置づけ (AGENTS.mdの約束を参照)。取得の詳細は
[pipeline.md の「落とさずに読む」](pipeline.md) にある。

### Mapterhorn の標高タイル

地形表示に使っている。[attribution.json](https://download.mapterhorn.com/attribution.json) に
ソース一覧があり、**日本は基盤地図情報 (数値標高モデル)** で `jpdem1a` (1m)・`jpdem5a` (5m)・
`jpdem10a` / `jpdem10b` (10m) を持つ。**1m版にも追従している。**

ライセンス欄に
「国土地理院コンテンツ利用規約／**測量法に基づく国土地理院長承認（使用）R 7JHs 542**」とあり、
測量成果の使用承認はMapterhorn側が取得している。こちらは配信されているタイルを
**実行時に読むだけ**なので、地理院タイルをベースマップに使っているのと同じ立場になる。
出典は `tilejson.json` の `attribution` をMapLibreがそのまま表示する
(手で書き足していないので、向こうが文言を変えれば追随する)。

`tilejson.json` の実測値:

| 項目 | 値 |
| --- | --- |
| encoding | `terrarium` (**MSL基準**。楕円体高ではないのでジオイド補正は不要) |
| tileSize | 512 |
| maxzoom | **宣言が無い。実際は z16 まで** (z17以降は404) |

maxzoom が宣言されていないので、ソース定義側で `maxzoom: 16` を明示している。
入れないと、建物を見るズーム (15以上) で404を撃ち続ける。

### PLATEAUのDEMを表示に使わない理由

PLATEAUのCityGMLには地形モデル (`dem:TINRelief`) が同梱されているが、**表示には使わない。**

港区の `udx/dem/533946_dem_6697_op.gml` を展開せずに測った結果:

| | 実測値 |
| --- | --- |
| 三角形の辺の長さ | **5.00m と 7.08m のみ** (7.08 = 5×√2) |
| 4メッシュ分の展開後サイズ | **960 MB** |

**TINといっても5mグリッドを三角形に割っただけ**で、5mラスタと情報量が同じ。
「TINだから正確」ではない。表示用にこれをラスタタイルへ焼く工程を持つ意味がない。

必要になるとすれば、**表示ではなく計算に使う標高**が欲しくなったとき
(空間IDのボクセル化など)。標高タイルは表示専用で、SQLからは引けない。

### 承認が不要なのは「タイル」であって「元データ」ではない

**この区別が重要。** 地理院のデータが一律に使えるようになったわけではない。

| | 位置づけ | 測量法の承認 |
| --- | --- | --- |
| ベクトルタイル (`experimental_bvmap` / `optimal_bvmap`) | 基本測量成果**ではない** | **不要** |
| その元データ ([数値地図（国土基本情報）](https://www.gsi.go.jp/kibanjoho/kibanjoho40027.html)) | **基本測量成果** | **必要** |

タイルの生成元である「数値地図（国土基本情報）- 地図情報」は基本測量成果なので、
[測量法第29条(複製)・第30条(使用)](https://www.gsi.go.jp/LAW/2930-index.html)の承認が要る。
このパイプラインがやることは「加工・編集して新たな成果品を作る」ので**第30条(使用)**に当たる。

ただし承認自体は**手数料が無料**で、申請から承認まで**約2週間**。
[測量成果ワンストップサービス](https://www.gsi.go.jp/LAW/2930-index.html)からオンラインで申請できる。
費用の問題ではなく手続きの手間の問題。

### 方針: 描画用データではなく元データを基準にする

**承認が要るとしても、基準にするのは数値地図 (元データ) の方にする。**
ベクトルタイルは承認が不要で手軽だが、**表示のために加工済み**であって、
測ったり判定したりする根拠にはならない。

PMTilesのメタデータに生成コマンドが残っており、`tippecanoe -S 2 -Z 14 -z 16` で
簡略化されていることが確認できる。具体的に失われているもの:

| | タイルでの劣化 |
| --- | --- |
| 座標 | タイル内整数 (4096分割) に量子化。z16で約0.15m、z14で約0.6m |
| ライン・ポリゴン | `-S 2` で簡略化され、タイル境界で分割・重複する |
| ズーム | z14〜16の範囲でしか作られていない |

ドローンの経路や空域を判定する用途では、**「どれだけずれているか分からないデータ」を
根拠にできない**。名称 (注記) のように量子化が効かないものだけはタイルで足りるが、
形状が要るものは元データを取る。

したがって**申請は「必要になった時点で」ではなく、必要が見えた時点で早めに出す**。
約2週間の待ちがあるので、他の作業と並行できる。

一方、ベクトルタイルはどちらも**基本測量成果ではない**と明記されている。

> 本提供実験のベクトルタイルは**基本測量成果と位置付けているものではありません**が、
> 基本測量成果としての提供を検討するにあたって、提供を行うものです。
> — [gsimaps-vector-experiment README](https://github.com/gsi-cyberjapan/gsimaps-vector-experiment)

最適化ベクトルタイル側にも同趣旨の記載がある。したがって**承認申請は不要で、出典明示のみ**で使える。

出典の文言は各リポジトリが指定している。

- 提供実験版: 「国土地理院ベクトルタイル提供実験」
- 最適化版: 「国土地理院最適化ベクトルタイル」

加工した場合は加工した旨も併記する (国土地理院コンテンツ利用規約)。
`pipeline/src/catalog.rs` の `Attribution` に足す際は、既存の `MLIT_ISJ` / `MLIT_KSJ` と同じ体裁にする。

### 注意点

いずれも**試験公開**であり、「公開期間は公開終了まで」「URLやデータ構成、データの内容
(属性の有無や名称等)が変わる可能性があります」と明記されている。恒久的な依存先にはできない。
また将来 基本測量成果として提供される場合、承認が必要な位置づけに変わる可能性がある。

### タイルを元データとして使えるか

タイルは表示用に加工済みなので、原典の代わりにはならない。
PMTilesのメタデータに生成コマンドが残っており、tippecanoeで簡略化されていることが確認できる。

```
tippecanoe -P -f -q -pf -pk -S 2 -Z 14 -z 16 -B 14 -o output/tiles-25k.mbtiles
```

| | タイルから取る場合の劣化 |
| --- | --- |
| **注記(点)** | 座標がタイル内整数(4096分割)に量子化される。z16で約0.15m、z14で約0.6m。**実用上は問題にならない** |
| ライン・ポリゴン | `-S 2` で簡略化され、タイル境界で分割・重複する。**原典の代わりにはならない** |

つまり**名称(注記)が目的ならタイルで十分**で、形状の精度が要るなら元データに承認申請が要る。

## 2. 地理院ベクトルタイルの中身

### 2つの製品の関係

データの鮮度は同じ(どちらも2026年4月1日時点)。並行して維持されている。
最適化版が設計上の後継にあたる。

> 「最適化ベクトルタイル」は、これまで地理院地図Vectorにおいて試験提供してきた
> 地理院ベクトルタイルの課題を踏まえて、**設計改良を施したもの**です。
> — [optimal_bvmap readme](https://github.com/gsi-cyberjapan/optimal_bvmap)

| | 提供実験版 (`experimental_bvmap`) | 最適化版 (`optimal_bvmap-v1`) |
| --- | --- | --- |
| 開始 | 2019-07-29 | 2022-09-06 |
| データ時点 | 2026年4月1日 | 2026年4月1日 |
| 配信 | XYZ (pbf) | XYZ (pbf) + **PMTiles 1ファイル** |
| 同一タイルの容量 | 178 KB | 78 KB |
| 名称の読み仮名 | **あり** (`kana`) | なし |

### 決定的な差: 読み仮名

**提供実験版の `label` レイヤは漢字と読み仮名を対で持っている。** 最適化版には無い。

| | 属性 |
| --- | --- |
| 提供実験版 `label` | `ftCode`, `annoCtg`, **`knj`**, **`kana`**, `arrng`, `arrngAgl`, `orgGILvl` |
| 最適化版 `Anno` | `vt_code`, **`vt_text`**, `vt_arrng`, `vt_arrngagl` |

実際の値(東京駅付近 z14):

```
提供実験版: 二松學舍大 / にしょうがくしゃだい
            東京メトロ有楽町線 / とうきょうめとろゆうらくちょうせん
            北の丸公園 / きたのまるこうえん
            皇居 / こうきょ
最適化版:   乾門, 御所, 皇居, 二重橋, 東京駅, 桜田門, 宮内庁 …(読みなし)
```

読み仮名は、かな入力での検索や表記ゆれの吸収に直接効く。**検索用途では提供実験版が有利**。

### 名称はすべて注記レイヤに集約されている

**両製品とも、名称は注記レイヤ(`label` / `Anno`)にしか無い。** 河川・建物・道路などの
ジオメトリ側には名前が付いていない。

| レイヤ (最適化版) | 地物数(全国) | 属性 |
| --- | ---: | --- |
| `Anno` (注記) | 62,397,259 | `vt_text`, `vt_code`, 配置情報 |
| `BldA` (建物) | 80,355,531 | `vt_code`, `vt_lvorder` — **名前も高さも用途も無し** |
| `RdCL` (道路中心線) | 95,367,546 | 種別・幅員・有料区分など9項目。**名前は無し** |
| `RvrCL` (河川中心線) | — | `vt_code` のみ。**名前は無し** |
| `Cntr` (等高線) | 200,349,116 | `vt_alti` (標高) |
| `AdmArea` (行政区画) | 3,225,116 | `vt_code` のみ |

つまり「多摩川」という名前を河川ジオメトリに結びつけたい場合、**注記レイヤから
空間的に対応付ける処理が別途必要**になる。名前付きの河川データが欲しいなら、
国土数値情報の河川データなど別の出所を当たる方が早い可能性が高い。

### 建物の属性は地理院でも解決しない

提供実験版の `building`、最適化版の `BldA` とも `ftCode` と `lvOrder` のみで、
高さも用途も名称も持たない。**建物の属性が欲しいならPLATEAU**という結論は変わらない。

## 3. 属性の充実度 (物差しを揃えた比較)

列ごとの非NULL率で測る。Overtureの建物を基準線とする。

| データセット | 件数 | 名称 | 種別・用途 | 高さ |
| --- | ---: | ---: | ---: | ---: |
| Overture 建物 (港区) | 24,345 | 13.6% | 8.9% (`class`) | 1.5% (`height`) |
| **PLATEAU 建物 (港区周辺)** | **51,170** | **0.6%** | **100%** (`usage`) | **100%** (`measuredHeight`) |
| 地理院 建物 (`BldA`) | 80,355,531 | 0% | — (`vt_code`は地物種別) | 0% |
| 地理院 注記 (`Anno`) | 62,397,259 | 100% | 100% (`vt_code`) | — |

再現用のクエリ:

```sh
mise exec -- duckdb -c "
SELECT count(*) AS 件数,
  round(100.0 * count(name)   / count(*), 1) AS 'name %',
  round(100.0 * count(class)  / count(*), 1) AS 'class %',
  round(100.0 * count(height) / count(*), 1) AS 'height %'
FROM read_parquet('data/output/overture_buildings_minato.parquet');"
```

地理院側は15.7GBのPMTilesを落とさずに、**ヘッダとメタデータの6.6KBだけをHTTP Rangeで取得**して
`tilestats` から件数と属性を読んだ (このリポジトリがGeoParquetでやっている部分取得と同じ考え方)。

## 4. PLATEAU の建物属性

`13103_minato-ku_pref_2025_citygml_1_op.zip` (2.0GB、展開後8.85GB / 57,278ファイル) で計測。
**zipは展開していない。** 中央ディレクトリから建物GMLのエントリだけを選び、
`unzip -p` で1本ずつストリーム展開して数えた (2.0GB / 51,170棟を約30秒)。

```sh
# 建物GMLのエントリだけを一覧 (中央ディレクトリのみ読むので一瞬)
unzip -l "$ZIP" | awk 'NF>=4 && $1 ~ /^[0-9]+$/ && $4 ~ /udx\/bldg\/.*\.gml$/ {print $4}' > list.txt

# 選んだエントリだけをストリームして数える
while read -r f; do unzip -p "$ZIP" "$f"; done < list.txt \
| awk '/<bldg:Building /{b++} /<bldg:measuredHeight/{h++} /<bldg:usage/{u++} /<gml:name/{n++}
       END {printf "建物=%d height=%.1f%% usage=%.1f%% name=%.1f%%\n", b, 100*h/b, 100*u/b, 100*n/b}'
```

### 計測結果 (51,170棟)

**「付与率100%」と「使える率」は違う。** 数値属性には `9999` / `-9999` という
「不明」の番兵値が紛れており、そのまま通すと絞り込みも row group の統計も壊れる
(変換時にNULLへ落としている。`pipeline/src/plateau.rs` を参照)。

| 属性 | 付与率 | 番兵値を除いた実質 |
| --- | ---: | ---: |

| `bldg:storeysAboveGround` (階数) | 100.0% | **85.2%** (`9999` が14.8%) |
| `bldg:usage` (用途) | 100.0% | **86.3%** (「不明」が13.7%) |

それでもOvertureの1.5% / 8.9%とは桁が違う。

| `bldg:usage` (用途) | **100.0%** |

## 5. わかったこと

1. **PLATEAUは建物属性を完全に解決する。** 高さ・用途・階数が100%。Overtureの1.5% / 8.9%とは
   桁が違う。加えて耐火構造・用途地域・建蔽率・容積率まで揃っている
2. **ただし名前は無い (0.6%)。** 建物名で探す用途には使えない。
   Overture (13.6%) の方がまだ名前を持っている
3. **属性が構造化されているので、意味検索より素のSQLが適している。**
   `usage` も `districtsAndZonesType` もコードリスト値で、高さ・階数・建蔽率は数値。
   `WHERE measuredHeight > 60 AND usage = '454'` で足りる話に、埋め込みを持ち出す理由がない。
   意味検索が効くのは自由記述のテキストがある場合で、PLATEAUの建物はそれに当たらない
4. **地理院はタイルなら承認不要だが、元データ(基本測量成果)には第30条の承認が要る。**
   ただし手数料無料・約2週間なので、形状の精度が要るなら申請する価値はある
5. **名称が欲しいなら地理院の注記レイヤ。** 読み仮名まで欲しければ提供実験版。
   ただしジオメトリとは分離しているので、河川名・建物名にするには空間的な対応付けが要る
6. 注記は全国6,240万件。384次元float32の埋め込みを全件に持たせると約96GBで**非現実的**。
   意味検索に使うなら注記分類で絞るか、低ズーム(=重要度の高い)注記に限る必要がある

## 6. 属性フィルタと row group 枝刈りの関係 (実測)

PLATEAUの建物を高さで絞ったときに、転送量がどう変わるかを測った
(港区・ズーム16・7.3MBのファイルに対して)。

| 高さの下限 | 転送量 | 表示件数 |
| --- | ---: | ---: |
| 0m (絞らない) | 2,724 KB | 1,784件 |
| 60m以上 | **2,724 KB** (変わらない) | 27件 |
| 150m以上 | 1,970 KB (28%減) | 4件 |

**属性フィルタでは row group 枝刈りはほとんど効かない。** 理由は並べ替えの軸にある。
配信用の最適化 ([`spatial_pack`](../pipeline/src/spatial_pack.rs)) は行を**空間的に**
並べ替えるので、どの row group にも低い建物と高い建物が混ざる。
結果として全 row group の高さ統計が「0.6m〜200m前後」になり、
`height >= 60` では1つも枝刈りできない。

```
row_group  height min  max
0          1.5        172.7
1          0.8        235.0
2          0.6        224.6   ← どれも全域をまたぐ
3          0.6        211.5
4          1.2        332.1
5          3.0        212.4
```

150mでようやく減るのは、ページ単位の統計で一部が飛ばせるようになるため。

**枝刈りが効くのは空間フィルタ (bbox)。** 7.3MBのうち表示範囲分の2.7MBしか読んでおらず、
covering bbox による絞り込みはきちんと働いている。

したがって属性フィルタの利点は転送量ではなく、次の2つ:

1. **描画する地物が減る** (1,784件 → 27件)。ブラウザの描画負荷に効く
2. **2回目以降の絞り込みは通信ゼロ**。一度読んだ row group はDuckDB側にあるので、
   スライダーを動かしても再取得が起きない

数値属性で枝刈りを効かせたいなら、その属性を並べ替えの軸に含める必要がある
(ただし空間的な枝刈りとトレードオフになる)。

### 傾けたときの取得範囲

建物は `fill-extrusion` で立体に描いており、高さを持つ出所を選ぶと地図が傾く。
**傾けると `map.getBounds()` は地平線方向へ大きく広がる。**

| 傾き | 範囲の面積 | 読む量 |
| ---: | ---: | ---: |
| 0度 | 1.0倍 | 2,724 KB |
| 30度 | 1.5倍 | — |
| 50度 | 3.1倍 | **2,724 KB** (変わらない) |
| 60度 | 7.1倍 | 6,084 KB (2.2倍) |

範囲が3倍に広がっても読む量が変わらないのは、取得を**画面中心からの距離順**に
並べて上限で切っているため。遠景が落ちるだけで、新しい row group を読みに行かない。
60度まで倒すとさすがに増えるので、傾きは**50度**にしてある。

### 次の一手の候補

意味検索の材料を探す調査だったが、**見つかったのは「意味検索より構造化クエリが要る」という答え**だった。

- **PLATEAUで属性フィルタ付きの建物表示** — 以前アイデアとして出ていた
  「ドローン運用者向けに高さや用途で建物を絞る」がそのまま実現できる。
  意味検索も埋め込みモデルも要らず、今のGeoParquet + row group枝刈りの延長で成立する
- 意味検索を試すなら、自由記述テキストを持つデータ (施設の説明文など) を別途探す必要がある
