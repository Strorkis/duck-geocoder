# データ源の調査

意味検索(埋め込みによる類似検索)の材料になるデータを探すための調査。
**権利面を先に確認し、使えるものだけ属性を測る**という順で進めた。

調査日: 2026-09-06

## 1. 権利面

| データ源 | ライセンス | 測量法の承認 | 加工・再配布 | 判定 |
| --- | --- | --- | --- | --- |
| [地理院ベクトルタイル提供実験](https://github.com/gsi-cyberjapan/gsimaps-vector-experiment) | [国土地理院コンテンツ利用規約](https://www.gsi.go.jp/kikakuchousei/kikakuchousei40182.html) (PDL 1.0) | **不要** | 可 | ✅ 使える |

### 承認が不要なのは「タイル」であって「元データ」ではない

**この区別が重要。** 地理院のデータが一律に使えるようになったわけではない。

| | 位置づけ | 測量法の承認 |
| --- | --- | --- |
| ベクトルタイル (`experimental_bvmap` / `optimal_bvmap`) | 基本測量成果**ではない** | **不要** |
| その元データ ([数値地図（国土基本情報）](https://www.gsi.go.jp/kibanjoho/kibanjoho40027.html)) | **基本測量成果** | **必要** |

タイルの生成元である「数値地図（国土基本情報）- 地図情報」は基本測量成果なので、
[測量法第29条(複製)・第30条(使用)](https://www.gsi.go.jp/LAW/2930-index.html)の承認が要る。
このパイプラインがやることは「加工・編集して新たな成果品を作る」ので**第30条(使用)**に当たる。

ただし承認自体は**手数料が無料**で、申請から承認まで**約2週間**。
[測量成果ワンストップサービス](https://www.gsi.go.jp/LAW/2930-index.html)からオンラインで申請できる。
費用の問題ではなく手続きの手間の問題なので、必要になった時点で判断すればよい。

一方、ベクトルタイルはどちらも**基本測量成果ではない**と明記されている。

> 本提供実験のベクトルタイルは**基本測量成果と位置付けているものではありません**が、
> 基本測量成果としての提供を検討するにあたって、提供を行うものです。
> — [gsimaps-vector-experiment README](https://github.com/gsi-cyberjapan/gsimaps-vector-experiment)

最適化ベクトルタイル側にも同趣旨の記載がある。したがって**承認申請は不要で、出典明示のみ**で使える。

出典の文言は各リポジトリが指定している。

- 提供実験版: 「国土地理院ベクトルタイル提供実験」
- 最適化版: 「国土地理院最適化ベクトルタイル」

加工した場合は加工した旨も併記する (国土地理院コンテンツ利用規約)。
`pipeline/src/catalog.rs` の `Attribution` に足す際は、既存の `MLIT_ISJ` / `MLIT_KSJ` と同じ体裁にする。

### 注意点

いずれも**試験公開**であり、「公開期間は公開終了まで」「URLやデータ構成、データの内容
(属性の有無や名称等)が変わる可能性があります」と明記されている。恒久的な依存先にはできない。
また将来 基本測量成果として提供される場合、承認が必要な位置づけに変わる可能性がある。

### タイルを元データとして使えるか

タイルは表示用に加工済みなので、原典の代わりにはならない。
PMTilesのメタデータに生成コマンドが残っており、tippecanoeで簡略化されていることが確認できる。

```
tippecanoe -P -f -q -pf -pk -S 2 -Z 14 -z 16 -B 14 -o output/tiles-25k.mbtiles
```

| | タイルから取る場合の劣化 |
| --- | --- |
| **注記(点)** | 座標がタイル内整数(4096分割)に量子化される。z16で約0.15m、z14で約0.6m。**実用上は問題にならない** |
| ライン・ポリゴン | `-S 2` で簡略化され、タイル境界で分割・重複する。**原典の代わりにはならない** |

つまり**名称(注記)が目的ならタイルで十分**で、形状の精度が要るなら元データに承認申請が要る。

## 2. 地理院ベクトルタイルの中身

### 2つの製品の関係

データの鮮度は同じ(どちらも2026年4月1日時点)。並行して維持されている。
最適化版が設計上の後継にあたる。

> 「最適化ベクトルタイル」は、これまで地理院地図Vectorにおいて試験提供してきた
> 地理院ベクトルタイルの課題を踏まえて、**設計改良を施したもの**です。
> — [optimal_bvmap readme](https://github.com/gsi-cyberjapan/optimal_bvmap)

| | 提供実験版 (`experimental_bvmap`) | 最適化版 (`optimal_bvmap-v1`) |
| --- | --- | --- |
| 開始 | 2019-07-29 | 2022-09-06 |
| データ時点 | 2026年4月1日 | 2026年4月1日 |
| 配信 | XYZ (pbf) | XYZ (pbf) + **PMTiles 1ファイル** |
| 同一タイルの容量 | 178 KB | 78 KB |
| 名称の読み仮名 | **あり** (`kana`) | なし |

### 決定的な差: 読み仮名

**提供実験版の `label` レイヤは漢字と読み仮名を対で持っている。** 最適化版には無い。

| | 属性 |
| --- | --- |
| 提供実験版 `label` | `ftCode`, `annoCtg`, **`knj`**, **`kana`**, `arrng`, `arrngAgl`, `orgGILvl` |
| 最適化版 `Anno` | `vt_code`, **`vt_text`**, `vt_arrng`, `vt_arrngagl` |

実際の値(東京駅付近 z14):

```
提供実験版: 二松學舍大 / にしょうがくしゃだい
            東京メトロ有楽町線 / とうきょうめとろゆうらくちょうせん
            北の丸公園 / きたのまるこうえん
            皇居 / こうきょ
最適化版:   乾門, 御所, 皇居, 二重橋, 東京駅, 桜田門, 宮内庁 …(読みなし)
```

読み仮名は、かな入力での検索や表記ゆれの吸収に直接効く。**検索用途では提供実験版が有利**。

### 名称はすべて注記レイヤに集約されている

**両製品とも、名称は注記レイヤ(`label` / `Anno`)にしか無い。** 河川・建物・道路などの
ジオメトリ側には名前が付いていない。

| レイヤ (最適化版) | 地物数(全国) | 属性 |
| --- | ---: | --- |
| `Anno` (注記) | 62,397,259 | `vt_text`, `vt_code`, 配置情報 |
| `BldA` (建物) | 80,355,531 | `vt_code`, `vt_lvorder` — **名前も高さも用途も無し** |
| `RdCL` (道路中心線) | 95,367,546 | 種別・幅員・有料区分など9項目。**名前は無し** |
| `RvrCL` (河川中心線) | — | `vt_code` のみ。**名前は無し** |
| `Cntr` (等高線) | 200,349,116 | `vt_alti` (標高) |
| `AdmArea` (行政区画) | 3,225,116 | `vt_code` のみ |

つまり「多摩川」という名前を河川ジオメトリに結びつけたい場合、**注記レイヤから
空間的に対応付ける処理が別途必要**になる。名前付きの河川データが欲しいなら、
国土数値情報の河川データなど別の出所を当たる方が早い可能性が高い。

### 建物の属性は地理院でも解決しない

提供実験版の `building`、最適化版の `BldA` とも `ftCode` と `lvOrder` のみで、
高さも用途も名称も持たない。**建物の属性が欲しいならPLATEAU**という結論は変わらない。

## 3. 属性の充実度 (物差しを揃えた比較)

列ごとの非NULL率で測る。Overtureの建物を基準線とする。

| データセット | 件数 | 名称 | 種別・用途 | 高さ |
| --- | ---: | ---: | ---: | ---: |
| Overture 建物 (港区) | 24,345 | 13.6% | 8.9% (`class`) | 1.5% (`height`) |
| **PLATEAU 建物 (港区周辺)** | **51,170** | **0.6%** | **100%** (`usage`) | **100%** (`measuredHeight`) |
| 地理院 建物 (`BldA`) | 80,355,531 | 0% | — (`vt_code`は地物種別) | 0% |
| 地理院 注記 (`Anno`) | 62,397,259 | 100% | 100% (`vt_code`) | — |

再現用のクエリ:

```sh
mise exec -- duckdb -c "
SELECT count(*) AS 件数,
  round(100.0 * count(name)   / count(*), 1) AS 'name %',
  round(100.0 * count(class)  / count(*), 1) AS 'class %',
  round(100.0 * count(height) / count(*), 1) AS 'height %'
FROM read_parquet('data/output/overture_buildings_minato.parquet');"
```

地理院側は15.7GBのPMTilesを落とさずに、**ヘッダとメタデータの6.6KBだけをHTTP Rangeで取得**して
`tilestats` から件数と属性を読んだ (このリポジトリがGeoParquetでやっている部分取得と同じ考え方)。

## 4. PLATEAU の建物属性

`13103_minato-ku_pref_2025_citygml_1_op.zip` (2.0GB、展開後8.85GB / 57,278ファイル) で計測。
**zipは展開していない。** 中央ディレクトリから建物GMLのエントリだけを選び、
`unzip -p` で1本ずつストリーム展開して数えた (2.0GB / 51,170棟を約30秒)。

```sh
# 建物GMLのエントリだけを一覧 (中央ディレクトリのみ読むので一瞬)
unzip -l "$ZIP" | awk 'NF>=4 && $1 ~ /^[0-9]+$/ && $4 ~ /udx\/bldg\/.*\.gml$/ {print $4}' > list.txt

# 選んだエントリだけをストリームして数える
while read -r f; do unzip -p "$ZIP" "$f"; done < list.txt \
| awk '/<bldg:Building /{b++} /<bldg:measuredHeight/{h++} /<bldg:usage/{u++} /<gml:name/{n++}
       END {printf "建物=%d height=%.1f%% usage=%.1f%% name=%.1f%%\n", b, 100*h/b, 100*u/b, 100*n/b}'
```

### 計測結果 (51,170棟)

**「付与率100%」と「使える率」は違う。** 数値属性には `9999` / `-9999` という
「不明」の番兵値が紛れており、そのまま通すと絞り込みも row group の統計も壊れる
(変換時にNULLへ落としている。`pipeline/src/plateau.rs` を参照)。

| 属性 | 付与率 | 番兵値を除いた実質 |
| --- | ---: | ---: |
| `bldg:measuredHeight` (高さ) | 100.0% | **95.6%** (`-9999` が4.4%) |
| `bldg:storeysAboveGround` (階数) | 100.0% | **85.2%** (`9999` が14.8%) |
| `bldg:usage` (用途) | 100.0% | **86.3%** (「不明」が13.7%) |

それでもOvertureの1.5% / 8.9%とは桁が違う。

| 属性 | 充足率 |
| --- | ---: |
| `bldg:measuredHeight` (高さ) | **100.0%** |
| `bldg:usage` (用途) | **100.0%** |
| `bldg:class` (分類) | **100.0%** |
| `bldg:storeysAboveGround` (地上階数) | **100.0%** |
| `uro:BuildingDetailAttribute` (詳細属性) | **100.0%** |
| `uro:buildingRoofEdgeArea` (屋根面積) | **100.0%** |

## 5. わかったこと

1. **PLATEAUは建物属性を完全に解決する。** 高さ・用途・階数が100%。Overtureの1.5% / 8.9%とは
   桁が違う。加えて耐火構造・用途地域・建蔽率・容積率まで揃っている
2. **ただし名前は無い (0.6%)。** 建物名で探す用途には使えない。
   Overture (13.6%) の方がまだ名前を持っている
3. **属性が構造化されているので、意味検索より素のSQLが適している。**
   `usage` も `districtsAndZonesType` もコードリスト値で、高さ・階数・建蔽率は数値。
   `WHERE measuredHeight > 60 AND usage = '454'` で足りる話に、埋め込みを持ち出す理由がない。
   意味検索が効くのは自由記述のテキストがある場合で、PLATEAUの建物はそれに当たらない
4. **地理院はタイルなら承認不要だが、元データ(基本測量成果)には第30条の承認が要る。**
   ただし手数料無料・約2週間なので、形状の精度が要るなら申請する価値はある
5. **名称が欲しいなら地理院の注記レイヤ。** 読み仮名まで欲しければ提供実験版。
   ただしジオメトリとは分離しているので、河川名・建物名にするには空間的な対応付けが要る
6. 注記は全国6,240万件。384次元float32の埋め込みを全件に持たせると約96GBで**非現実的**。
   意味検索に使うなら注記分類で絞るか、低ズーム(=重要度の高い)注記に限る必要がある

## 6. 属性フィルタと row group 枝刈りの関係 (実測)

PLATEAUの建物を高さで絞ったときに、転送量がどう変わるかを測った
(港区・ズーム16・7.3MBのファイルに対して)。

| 高さの下限 | 転送量 | 表示件数 |
| --- | ---: | ---: |
| 0m (絞らない) | 2,724 KB | 1,784件 |
| 60m以上 | **2,724 KB** (変わらない) | 27件 |
| 150m以上 | 1,970 KB (28%減) | 4件 |

**属性フィルタでは row group 枝刈りはほとんど効かない。** 理由は並べ替えの軸にある。
配信用の最適化 ([`spatial_pack`](../pipeline/src/spatial_pack.rs)) は行を**空間的に**
並べ替えるので、どの row group にも低い建物と高い建物が混ざる。
結果として全 row group の高さ統計が「0.6m〜200m前後」になり、
`height >= 60` では1つも枝刈りできない。

```
row_group  height min  max
0          1.5        172.7
1          0.8        235.0
2          0.6        224.6   ← どれも全域をまたぐ
3          0.6        211.5
4          1.2        332.1
5          3.0        212.4
```

150mでようやく減るのは、ページ単位の統計で一部が飛ばせるようになるため。

**枝刈りが効くのは空間フィルタ (bbox)。** 7.3MBのうち表示範囲分の2.7MBしか読んでおらず、
covering bbox による絞り込みはきちんと働いている。

したがって属性フィルタの利点は転送量ではなく、次の2つ:

1. **描画する地物が減る** (1,784件 → 27件)。ブラウザの描画負荷に効く
2. **2回目以降の絞り込みは通信ゼロ**。一度読んだ row group はDuckDB側にあるので、
   スライダーを動かしても再取得が起きない

数値属性で枝刈りを効かせたいなら、その属性を並べ替えの軸に含める必要がある
(ただし空間的な枝刈りとトレードオフになる)。

### 傾けたときの取得範囲

建物は `fill-extrusion` で立体に描いており、高さを持つ出所を選ぶと地図が傾く。
**傾けると `map.getBounds()` は地平線方向へ大きく広がる。**

| 傾き | 範囲の面積 | 読む量 |
| ---: | ---: | ---: |
| 0度 | 1.0倍 | 2,724 KB |
| 30度 | 1.5倍 | — |
| 50度 | 3.1倍 | **2,724 KB** (変わらない) |
| 60度 | 7.1倍 | 6,084 KB (2.2倍) |

範囲が3倍に広がっても読む量が変わらないのは、取得を**画面中心からの距離順**に
並べて上限で切っているため。遠景が落ちるだけで、新しい row group を読みに行かない。
60度まで倒すとさすがに増えるので、傾きは**50度**にしてある。

### 次の一手の候補

意味検索の材料を探す調査だったが、**見つかったのは「意味検索より構造化クエリが要る」という答え**だった。

- **PLATEAUで属性フィルタ付きの建物表示** — 以前アイデアとして出ていた
  「ドローン運用者向けに高さや用途で建物を絞る」がそのまま実現できる。
  意味検索も埋め込みモデルも要らず、今のGeoParquet + row group枝刈りの延長で成立する
- 意味検索を試すなら、自由記述テキストを持つデータ (施設の説明文など) を別途探す必要がある
