# データ源の調査

**権利面を先に確認し、使えるものだけ属性を測る**という順で進める。

もとは意味検索 (埋め込みによる類似検索) の材料を探す調査だった (2026-09-06)。
その後ドローン向けという方向が決まったので、**何が要るか**を先頭に置いた (2026-09-13)。

## 0. 何が要るか、どこから取るか

表にしてから取りに行く。**

### 参考にした仕様 (どんなデータが求められているかの手掛かり)

**このリポジトリの目的ではない。** どんなデータが求められているかを知るために
読んだ資料として残す。

NEDO「ドローン航路導入ガイドライン Ver2.0(案)」(2026年3月) と附属書
(`.reference/UASL/`)。ドローンの運航管理では、地理空間情報・気象・電波・人口統計を
供給する役割が **SDSP (情報提供サービスプロバイダ)** と呼ばれ、そのデータモデルを
**ISO 23629-7** (日本発、2021年発行) が規格化している。

| ISO 23629-7 の層 | 中身 | ここにあるもの |
| --- | --- | --- |
| 地図情報 (0m〜) | 地形、離着陸エリア | 地形 **あり** / 離着陸 無し |
| 障害物情報 (0〜100m) | 建物・鉄塔 | 建物 **あり (港区のみ)** / 鉄塔 出所なし |
| 仮想データ (0〜150m) | 飛行禁止エリア、航路 | 無し |
| 動的データ (0〜150m) | 気象、他機位置 | **ファイルで配るものではない** |

**層の切り方が参考になる。** 静的なもの (地図・障害物・仮想) は
ファイルとして配れて、動的なもの (気象・他機位置) は配れない。
このリポジトリが扱えるのは前者。

#### 人流 — オープンデータは更新が止まっている (調査済み・2026-09)

表の「人流」は**移動滞在データ (過去データ)** で、いま入れている
国勢調査の人口メッシュとは違う。国勢調査は**常住人口 (夜間人口)** なので、
オフィス街の昼間や駅周辺のラッシュを表さない。
地上リスクを常住人口だけで見ていると、**昼間の都心を過小評価する。**

**国土交通省「全国の人流オープンデータ」は終わっている。**

| | |
| --- | --- |
| 中身 | 1kmメッシュ別の滞在人口 / 市区町村単位発地別。平日・休日、昼・夜 |
| 収録 | **2019年1月〜2021年12月** |
| 更新 | **「2022年以降の公開予定はございません」と明記** |
| 形式 | CSV。ダウンロードに**ユーザ登録が必要** |
| 規約 | 政府標準利用規約 |

[G空間情報センター](https://www.geospatial.jp/ckan/dataset/mlit-1km-fromto) にある。
**コロナ対策調査の一環**として出されたもので、収録期間もその3年間。
運航の判断の土台には置けない。

**代わりになるのは国勢調査の別集計。**

> 令和4年12月13日公表
> **「令和2年国勢調査に関する地域メッシュ統計 (人口移動、就業状態等及び従業地・通学地)」**
> (JGD2011版もあり)

**いま使っている人口メッシュと同じ配信・同じCSV形式・同じメッシュコード**なので、
`pipeline/src/mesh_pop.rs` の項目名を差し替えるだけで読める
(項目は名前で引いて、無ければ候補を並べて落とす作りにしてある)。
これで「そのメッシュで働く人・学ぶ人の数」が取れる。

有償なら他にもある (モバイル空間統計、KDDI Location Analyzer、Agoop)。
**無償で全国かつ継続更新となると、国勢調査系が実質唯一。**

#### 鉄道ダイヤ — オープンだが、ここでは扱わない (調査済み・2026-09-19)

[公共交通オープンデータセンター (ODPT)](https://www.odpt.org/) が列車時刻表を
配信している。[開発者サイト](https://developer.odpt.org/)で登録すると**無料**の
APIキーが取れ、JR東日本の GTFS、GTFS-RT の列車ロケーションもある。

**人流と同じ問題意識に効く。** ダイヤが分かると、鉄道は「静的な線」ではなく
**時間で変わるリスク**になる (列車がいる時だけ人が集まる)。

**それでもこのリポジトリでは扱わない。** 理由は既存の線引きと同じ:

- 価値のある部分 (列車ロケーション) は**動的データ**で、ファイルで配るものではない
- ODPTのガイドラインが**取得日時の表示**を求めている。静的配布と噛み合わない
- APIキーが要る

**動的データ側でやりたくなったときのために** `.reference/` に引き継ぎ資料を置いた
(git管理外)。

#### 全国のDSM — 30mが限界 (調査済み・2026-09)

PLATEAUの無い地域の障害物を埋める候補。どちらも全球をカバーする。

| | 提供 | 解像度 | 制約 |
| --- | --- | ---: | --- |
| [Copernicus DEM GLO-30](https://dataspace.copernicus.eu/) | ESA | 30m | **free & open** |
| [AW3D30](https://www.eorc.jaxa.jp/ALOS/jp/dataset/aw3d30/aw3d30_j.htm) | JAXA | 30m | **平和利用目的に限定**。商用は事前通知。高さ精度5m (標準偏差) |

DSMからDEM (基盤地図情報) を引けば **nDSM = 地物の高さ** が全国で出る。
ただし**30mメッシュなので市街地では建物1棟が均される。**
森林のように広く一様なものには効く。

**精度でいえば自治体の点群の方が桁違いに上** (静岡は16点/m²)。
全国を粗く覆うか、あるところを精密に持つかは別の話で、**どちらも価値がある。**

#### COPC と GeoParquet の使い分け

**排他ではなく層が違う。**

| | COPC | GeoParquet |
| --- | --- | --- |
| 得意 | 3D点群のLODストリーミング、範囲抽出 | 属性クエリ、他データとの結合 |
| 位置づけ | **実データの配信層** | **属性・カタログ層** |

点群を配るならCOPCを足す形になるが、**カタログは同じSTACのまま。**
STACは形式を問わず、Itemのアセットとして載る
(Portolanが「ベクタはGeoParquet + PMTiles、ラスタはCOG、点群はCOPC」を
1つの仕様にしているのはそのため)。

#### 気象 — Open-Meteo は非商用なら使える

| | |
| --- | --- |
| データ | **CC BY 4.0** (商用も可) |
| 無料のホストAPI | **非商用限定**。10,000コール/日、稼働保証なし |
| 商用 | サブスクリプション (専用エンドポイント) |
| 自前ホスト | AGPLv3 |

**データのライセンスとサービスの規約が別。** CC BY 4.0 は無料エンドポイントを
商用で使う許可にはならない。出典表示は必須。

**これはファイルを配るものではない** (実行時にAPIを叩く) ので、
カタログには載らない。入れるならプレビュー側の機能として。

### 出所ごとに何が言えるか

**全国を覆っているかどうかは、使う・使わないの基準にしない。**
静岡の点群 (16点/m²) は、全国を覆う30mメッシュのDSMより桁違いに精度が高い。
**あるところでは精度の高いものを使う。** 散らばっているデータを1つのカタログから
引けるようにすること自体が、このリポジトリの目的のひとつ。

> **訂正 (2026-09-16):** ここには以前「出所の格付け: 全国 × 公的なものを本線にする」
> という節があり、**「一部の地域でしか出ない答えは、運航の判断に使えない」**を理由に
> 自治体の点群などを落としていた。**これは書き手の一般化で、方針ではなかった。**
> 元になったのは送電線・鉄塔についての「OSMを使う以上すべてが参考」という判断で、
> そこから「全国 × 公的でなければ使わない」へ広げてしまったもの。撤回する。

**残る線引きは1つだけ。** OSM / Overture 由来のものを、安全に直結する値の
根拠にはしない。逆ジオコーディングや地図表示には十分だが、リスクの計算には使わない。

**収録範囲はカタログが持っている。** STACのItemがファイルごとに `bbox` を持つので、
「どこまで入っているか」は機械が読める。人が格付けで覚える必要はない。

行政区域は本来 国土数値情報 N03 に寄せたい。変換は実装済みだが、
**N03は複製に国土地理院長の承認が要る** (下の表) ので配信していない。

### SORA 2.5 の iGRC 表

色分けの区切りをこの表に合わせる。連続的なグラデーションだと「濃い/薄い」しか
読めないが、この段で切れば**地図がそのまま iGRC を答える**。

行が人口密度 (人/km²)、列が機体の最大特性寸法と最大速度。値は 1〜11。

| 最大人口密度 (人/km²) | 1m<br>25m/s | 3m<br>35m/s | 8m<br>75m/s | 20m<br>120m/s | 40m<br>200m/s |
| --- | :-: | :-: | :-: | :-: | :-: |
| Controlled Ground Area | 1 | 1 | 2 | 3 | 3 |
| < 5 | 2 | 3 | 4 | 5 | 6 |
| < 50 | 3 | 4 | 5 | 6 | 7 |
| < 500 | 4 | 5 | 6 | 7 | 8 |
| < 5,000 | 5 | 6 | 7 | 8 | 9 |
| < 50,000 | 6 | 7 | 8 | 9 | 10 |
| > 50,000 | 7 | 8 | **SORAの適用範囲外** | | |

- 250g以下かつ最大速度25m/s以下は、人口密度によらず **iGRC 1**
- 標準的な住宅を貫通しないと見込まれる機体は、大規模な人の集まりの上を飛ばない限り
  Step 3 の M1(A) (遮蔽) で **-1**
- 2.0の定性区分 (人口がまばら/密集など) が、2.5で**この数値**に置き換わった。
  建物や土地利用で当てはめていた判断が、人口密度の実測値で決まる形になる

**運航範囲の中で最も密度の高いところ**を採る。平均ではない。
集約するときに平均を取ると、危ないセルが薄まって消える。

出典: [JARUS SORA v2.5 Main Body (JAR_doc_25)](http://jarus-rpas.org/wp-content/uploads/2024/06/SORA-v2.5-Main-Body-Release-JAR_doc_25.pdf) Table 2。
**実装の前に原文を確認すること。** 安全に関わる数値なので、この写しを根拠にしない。

なお **iGRC は航空法の許可要否そのものではない。** 日本の特定飛行 (DIDや第三者上空) の
判定は別の層で、SORAはリスク評価の枠組み。

#### 地図での見せ方 (実装済み)

色の区切りを上の表の行に合わせてある (`IGRC_BANDS` in `web/src/main.ts`)。
**機体を選ぶと凡例の iGRC が変わる**が、地図の色は変わらない。
色は密度の帯で決まり、機体は帯から iGRC を引くときにだけ効くため。

**表示範囲の最大密度を数字でも出す。** SORAは運航範囲の中で最も密度の高いところを
採るので、地図から目で探させるより確実。

**束ねたセルは親メッシュの矩形で描く。** 当初は中に入っている子メッシュのbboxの和で
描いていたが、人のいる子だけを囲った形になり、左端の列にしか人がいない1kmセルが
細い縦帯になって地図がメッシュに見えなくなった。矩形はメッシュコードから計算する。
同じ階層のセルは全部同じ大きさになるので、E2Eで揃っていることを見ている。

メッシュの粗さはズームで変える (125m / 250m / 500m / 1km)。
**メッシュコードは階層なので、前から切るだけで粗くできる**
(`substr(mesh_code, 1, 8)` が1km)。集約用のファイルを別に作らずに済む。
束ねるときは**人口は合計、密度は最大**。平均にすると危ないセルが薄まって消える。

**引いた表示には、全国を1kmに束ねたファイルを別に配る。** 125mから束ねることも
できるが、引くほど元の行を多く読むことになる。実測 (東京中心):

| ズーム | 表示 | 125mから束ねる | **1kmファイルから** |
| ---: | --- | ---: | ---: |
| 13 | 500m | 2.3 MB | (125mを使う) |
| 11 | 1km | 約5 MB | **0.8 MB** |
| 7 | 10km | 21.1 MB | **2.2 MB** |
| 5 | 80km | (打ち切っていた) | **4.3 MB** |

どのファイルから引くかは `meshSourceFor` が決める。**要求する細かさを出せるものの中で、
いちばん粗いものを選ぶ。** 1kmのファイルで500mは描けないので、寄ったら125mに戻る。

全国を80kmで俯瞰しても最大密度は **217,219 人/km²** のまま。
これは全国の125mメッシュの最大値と一致する。束ねる途中で平均を取っていれば
桁ごと落ちるので、E2Eで見張っている。

### 地上リスクは人口密度だけにしない

SORAの iGRC は人口密度で決まるが、**それだけをリスク値にしない。**
実際の運航では「人がいるか」と別に「**落ちてはいけない場所か**」がある。

**リスクの種類で並べたもの** (調査日 2026-09-19)。都市数はPLATEAUの
[配信カタログAPI](https://api.plateauview.mlit.go.jp/datacatalog/plateau-datasets)
を集計した実数 (全307都市)。

| 道路 | 人と車がいる。墜落は二次事故になる | PLATEAU `tran` **302都市** / 国土数値情報 **N13** | N13は **CC BY 4.0**。ただし下記 |

| 点群由来の障害物面 | PLATEAU外を埋める | 自治体の点群 | 形式を決めるところから |

**► 飛ばしてはいけない場所**

| 重ねたいもの | なぜ | 出所 | 状況 |
| --- | --- | --- | --- |
| 空港と制限表面 | 空域 | 国土数値情報 **C28** (**商用可**) | 面は配られていないが**計算で作れる** (下記) |
| 小型無人機等飛行禁止法の対象施設 | 直罰の対象 | 警察庁 | **機械可読で配られていない** (下記) |

**► リスクを下げるもの**

| 重ねたいもの | なぜ | 出所 | 状況 |
| --- | --- | --- | --- |
| 水部 | **着水は選択肢になる** | PLATEAU `wtr` **57都市** / Overture | 未取得 |
| 土地利用・用途地域 | 緊急着陸地点を選ぶ | PLATEAU `luse` **291都市** / `urf` **284都市** | 未取得 |

**収録都市が少ないことは、使わない理由にしない。** `cons` が5都市でも、
**その5都市では鉄塔の高さが分かる**。下の「出所ごとに何が言えるか」を参照。

**設計の方針: 出所ごとに「メッシュに載るリスク面」を作り、重ね合わせで最終値を出す。**
1つの式に固め打ちしない。理由は3つ:

- **規格と運用がずれる。** SORAのiGRCは規格の値で、そこに独自の係数を混ぜると
  「規格に沿った値」が出せなくなる。**人口密度だけの層は独立に持ち、
  他は加算レイヤーとして分ける**
- **要る層が用途で変わる。** 目視外か目視内か、機体の大きさ、昼夜で効く層が違う
- **データの整備範囲が層ごとに違う。** 道路は302都市、水部は57都市。
  「無い層は寄与ゼロ」で成立する形にしておかないと、範囲の広い地域で使えない

メッシュの粒度は国勢調査のものをそのまま使う。**取り込んだのは125m (6次メッシュ)** で、
500m・1kmへはメッシュコードの切り出しと集約で落とせる (`substr(mesh_code, 1, 8)` が1km)。
細かい方を持っておけば粗い方は作れるが、逆はできない。

#### 人口メッシュは境界データを落とさなくてよい

**地域メッシュは経緯度から機械的に決まる方眼**で、測量成果ではない。3次メッシュ (約1km)
も、それを4分割した500mメッシュも、**メッシュコードから座標を計算で出せる**。

| | 取るもの | 測量法 |
| --- | --- | --- |
| 人口の値 | [e-Stat 統計GIS](https://www.e-stat.go.jp/gis) の地域メッシュ統計 | 対象外 (統計) |
| メッシュのジオメトリ | **自前で計算して作る** | **対象外** |

境界データのダウンロード自体が不要になるので、**測量法の懸念が原理的に発生しない**。
計算は決定的なのでRust側でテストも書ける (`pipeline/src/bin/` の流儀に合う)。

なお小地域 (町丁・字等) の境界データは測量成果に基づく図形を含むので扱いが違う。
**メッシュと混同しないこと。**

取得は [e-Stat API 3.0](https://www.e-stat.go.jp/api/) (バージョン3.0から小地域・
地域メッシュに対応) か、統計GISからの直接ダウンロード。**APIはユーザ登録して
アプリケーションIDを取る必要があり**、使った場合は次のクレジット表示が要る。

> このサービスは、政府統計総合窓口(e-Stat)のAPI機能を使用していますが、
> サービスの内容は国によって保証されたものではありません。

利用規約は**データ本体とAPI機能で別々**にあり、API側は短時間の大量アクセスを禁じている。

**建物以外の3D障害物は、点群がほぼ唯一の出所になる。** ただし生のままはTB級なので
**派生物にする** (間引き・メッシュごとの最高標高・障害物面の抽出など)。
**県全域まで整備されている所もある**ので、あるところでは使う。

いま入っているのは **建物 (PLATEAU) と地形 (Mapterhorn) の2つ**。
点群は形式と派生物の作り方を決めるところから ([roadmap.md](roadmap.md))。

### 点群のオープンデータ (調査済み・2026-09)

**結論を先に。**

1. **権利面は問題にならない。** 主要な県はCC BY 4.0で、商用も含めて二次利用できる。
   むしろ地理院の方が厳しい (測量法の申請が要り、受注生産)。
2. **送電線・鉄塔として分類された点群は無い。** 期待していた
   ASPRS Class 14 (電力線) / 15 (鉄塔) は入っていない。公開データの分類は
   **地表面か否か (DSM / DEM) までしか無い**。フィルタ一発では取れない。
3. **Rangeで直接読む設計にはなっていない。** 図郭ごとのZIP (平均200〜300MB、
   最大5.6GB) で、中身は圧縮済みのLAS。PLATEAUのように「必要な所だけ引く」が効かない。
   **持つなら派生物にする。**
4. **全国には無い。** 県全域まで来ているのは兵庫・山梨・長崎など数県。
   **ただし精度は桁違いに高い** (静岡は16点/m²、全国を覆うDSMは30mメッシュ)。
   **あるところでは使う**という整理 ([roadmap.md](roadmap.md) の「集めたいデータ」)。

#### 送電線・鉄塔が分類されていない理由

公開データの多くが **LAS 1.2** (レコードフォーマット2・3) で作られている。
ASPRSの標準分類でClass 14/15が**電力線・鉄塔に割り当てられたのは LAS 1.4
(レコードフォーマット6以降)** で、LAS 1.2では14も15も予約値でしかない。
**器が持てないものは入っていない。**

加えて、公共測量の作業規程が求める分類は数値標高モデルを作るためのもので、
地表面・建物・植生までしか分けない。地理院の点群も
[簡易分類 (地表・水部・その他)](https://www.gsi.go.jp/gazochosa/tengun.html) どまり。

#### 送電線・鉄塔は出所が無い

「位置はOSM (`power=tower`)、高さはその地点の点群の最高標高」という組み合わせは
技術的には成り立つ。**が、主軸にはしない** (2026-09-13の判断)。

理由は**OSMを使う以上どこまでも「参考」にしかならない**こと。障害物の有無は
安全に直結するので、出所は公的なものにしたい。

**点群から鉄塔を推定する (分類を自前でやる) のは研究の領分**で、
このリポジトリの仕事ではない。公的な出所が現れるまで空欄のままにする。

**点群そのものは別の話。** 地物の高さを測る材料としては使える
(派生物にしてから)。

#### Range で引けるか

引けない前提で設計する。図郭ごとのZIPで、中のLASは圧縮されている。
`remote_zip` で中央ディレクトリから1エントリを取り出すことはできるが、
**deflate圧縮されていれば先頭から流すしかない**ので、200MBのファイルから
一部分だけ、とはいかない。

ブラウザから引くなら [COPC](https://copc.io/) (Cloud Optimized Point Cloud) が
Range前提の形式だが、**国内の公開データにCOPCは見当たらない**。
変換するのはこちら側の仕事になる。TB級の生データをそのまま配る話ではなく、
**必要な派生物 (障害物の高さなど) を作って配る**方向で変わらない。

### 国土数値情報の読み方 (調査済み・2026-09-19)

**既定は公共データ利用規約 (PDL1.0)。承認が要るのは、基本測量成果を背景図・原典に
使っているものだけ**で、[利用規約](https://nlftp.mlit.go.jp/ksj/other/agreement.html)
が対象を列挙している (20万分の1土地分類基本調査、土地履歴調査、主要水系調査、
地下水調査など)。**正本は個別ページの「このデータの使用許諾条件」**なので、
データごとに読む。

#### 落とし穴が3つある

**1. 年度で条件が変わる。** P29 学校は2023年度版が CC BY 4.0 だが、
**2013年度版は非商用**。サイト側も「表示されている条件は最新版のもので、
旧版では異なる場合がある」と注意している。**旧年度を使うときは、その年度のページを読む。**

**2. ライセンス表記と測量法は別の話。** N13 道路は **CC BY 4.0** だが、原典に
**「測量法に基づく国土地理院長承認 (複製) R6JHf503」**と書かれている。
CC BY だから自由、とはならない。

**3. 承認番号が条文を示しているらしい。**

| 番号の形 | 条文 | 二次利用 |
| --- | --- | --- |
| `R6JHf503` — **f** | 第29条 **複製**承認 | さらに複製・使用するとき**申請が要る場合がある** |
| `R3JHs917` — **s** | 第30条 **使用**承認 | **申請不要** |

**これは番号の形からの推定で、裏は取れていない。** ただし当たっていれば、
**N13 道路 (複製) と P29 学校 (使用) では、こちらが負う義務が変わる。**
申請の前に国土地理院へ確認すること ([roadmap.md](roadmap.md) の測量法の節)。

なお**二次利用時は成果品名と承認番号の記載が要る**。出典表示に番号を載せる必要が
あるということで、これは「ライセンスを持ち回る」機能の要件になる。

### 配られていないもの・計算で作れるもの (調査済み・2026-09-19)

**小型無人機等飛行禁止法の対象施設は、機械可読では配られていない。**
警察庁が出しているのは**PDFの図面**で、地理院地図にレイヤ表示はあるが一括配布は無い。
**対象原子力事業所に至ってはWeb非公開**で、警察庁と関係する警察署への備え置きのみ。
**配れないので、このリポジトリでは扱えない。**

**空港の制限表面は、面のGISが全国一律には配られていない。** ただし
**航空法第2条が数式で定義している** — 進入表面は勾配 1/50、水平表面は標点の垂直上方
45mを中心とする半径4,000mの円、転移表面は外側上方へ 1/7。つまり
**C28 の標点と滑走路から計算で作れる**。`pipeline/src/mesh.rs` がメッシュ形状を
ダウンロードせず計算で作っているのと同じ型 (下の「人口メッシュは境界データを
落とさなくてよい」と同じ理屈)。

**ただし空港ごとに諸元が違う。** 大島空港は進入表面 1/40・水平表面 半径3,000m、
新島・神津島空港は 1/20・1,000m。**一律の式で全国を作ると間違える。**

### DID (人口集中地区) を保留している理由

**規約は読んだ。承認を求める記載はどちらにも無かった。**

対照として、**N03のページは「本製品を複製する場合には、国土地理院の長の承認を
得なければなりません」と明記している。** 書いてあるものには書いてある。

それでも保留にしているのは、**A16-2020の原典に「国土数値情報 (行政区域)」が
入っている**ため。A16自身の約款は承認を求めていないが、系譜としてN03を含む。
**行政区域の承認が下りたタイミングに合わせて実装する**という判断
(2026-09-16)。

系譜を避けたいだけなら、**原典が統計局だけのe-Stat版**という道が残る。
そちらはShapefile・都道府県別で、属性はA16より少ない。

**「書いていない」は「不要」の証明ではない。** どちらを使うにせよ、
商用に踏み込むときは発行元に当たること。

なお以前このドキュメントには「国土数値情報A16は平成27年止まり」と書いていたが、
**誤り**だった。見ていたのが `-v2_3` のページで、
[2020年版](https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-A16-2020.html) が別にある。
全国1ファイルのGeoJSONがあり、属性は15項目 (人口・面積・男女別・世帯数など)。

### Mapterhorn の標高タイル

地形表示に使っている。[attribution.json](https://download.mapterhorn.com/attribution.json) に
ソース一覧があり、**日本は基盤地図情報 (数値標高モデル)** で `jpdem1a` (1m)・`jpdem5a` (5m)・
`jpdem10a` / `jpdem10b` (10m) を持つ。**1m版にも追従している。**

ライセンス欄に
「国土地理院コンテンツ利用規約／**測量法に基づく国土地理院長承認（使用）R 7JHs 542**」とあり、
測量成果の使用承認はMapterhorn側が取得している。こちらは配信されているタイルを
**実行時に読むだけ**なので、地理院タイルをベースマップに使っているのと同じ立場になる。
出典は `tilejson.json` の `attribution` をMapLibreがそのまま表示する
(手で書き足していないので、向こうが文言を変えれば追随する)。

`tilejson.json` の実測値:

| 項目 | 値 |
| --- | --- |
| encoding | `terrarium` (**MSL基準**。楕円体高ではないのでジオイド補正は不要) |
| tileSize | 512 |
| maxzoom | **宣言が無い。実際は z16 まで** (z17以降は404) |

maxzoom が宣言されていないので、ソース定義側で `maxzoom: 16` を明示している。
入れないと、建物を見るズーム (15以上) で404を撃ち続ける。

### PLATEAUのDEMを表示に使わない理由

PLATEAUのCityGMLには地形モデル (`dem:TINRelief`) が同梱されているが、**表示には使わない。**

港区の `udx/dem/533946_dem_6697_op.gml` を展開せずに測った結果:

| | 実測値 |
| --- | --- |
| 三角形の辺の長さ | **5.00m と 7.08m のみ** (7.08 = 5×√2) |
| 4メッシュ分の展開後サイズ | **960 MB** |

**TINといっても5mグリッドを三角形に割っただけ**で、5mラスタと情報量が同じ。
「TINだから正確」ではない。表示用にこれをラスタタイルへ焼く工程を持つ意味がない。

必要になるとすれば、**表示ではなく計算に使う標高**が欲しくなったとき
(空間IDのボクセル化など)。標高タイルは表示専用で、SQLからは引けない。

### 承認が不要なのは「タイル」であって「元データ」ではない

**この区別が重要。** 地理院のデータが一律に使えるようになったわけではない。

| | 位置づけ | 測量法の承認 |
| --- | --- | --- |
| ベクトルタイル (`experimental_bvmap` / `optimal_bvmap`) | 基本測量成果**ではない** | **不要** |
| その元データ ([数値地図（国土基本情報）](https://www.gsi.go.jp/kibanjoho/kibanjoho40027.html)) | **基本測量成果** | **必要** |

タイルの生成元である「数値地図（国土基本情報）- 地図情報」は基本測量成果なので、
[測量法第29条(複製)・第30条(使用)](https://www.gsi.go.jp/LAW/2930-index.html)の承認が要る。
このパイプラインがやることは「加工・編集して新たな成果品を作る」ので**第30条(使用)**に当たる。

ただし承認自体は**手数料が無料**で、申請から承認まで**約2週間**。
[測量成果ワンストップサービス](https://www.gsi.go.jp/LAW/2930-index.html)からオンラインで申請できる。
費用の問題ではなく手続きの手間の問題。

### 方針: 描画用データではなく元データを基準にする

**承認が要るとしても、基準にするのは数値地図 (元データ) の方にする。**
ベクトルタイルは承認が不要で手軽だが、**表示のために加工済み**であって、
測ったり判定したりする根拠にはならない。

PMTilesのメタデータに生成コマンドが残っており、`tippecanoe -S 2 -Z 14 -z 16` で
簡略化されていることが確認できる。具体的に失われているもの:

| | タイルでの劣化 |
| --- | --- |
| 座標 | タイル内整数 (4096分割) に量子化。z16で約0.15m、z14で約0.6m |
| ライン・ポリゴン | `-S 2` で簡略化され、タイル境界で分割・重複する |
| ズーム | z14〜16の範囲でしか作られていない |

ドローンの経路や空域を判定する用途では、**「どれだけずれているか分からないデータ」を
根拠にできない**。名称 (注記) のように量子化が効かないものだけはタイルで足りるが、
形状が要るものは元データを取る。

したがって**申請は「必要になった時点で」ではなく、必要が見えた時点で早めに出す**。
約2週間の待ちがあるので、他の作業と並行できる。

一方、ベクトルタイルはどちらも**基本測量成果ではない**と明記されている。

> 本提供実験のベクトルタイルは**基本測量成果と位置付けているものではありません**が、
> 基本測量成果としての提供を検討するにあたって、提供を行うものです。
> — [gsimaps-vector-experiment README](https://github.com/gsi-cyberjapan/gsimaps-vector-experiment)

最適化ベクトルタイル側にも同趣旨の記載がある。したがって**承認申請は不要で、出典明示のみ**で使える。

出典の文言は各リポジトリが指定している。

- 提供実験版: 「国土地理院ベクトルタイル提供実験」
- 最適化版: 「国土地理院最適化ベクトルタイル」

加工した場合は加工した旨も併記する (国土地理院コンテンツ利用規約)。
`pipeline/src/catalog.rs` の `Attribution` に足す際は、既存の `MLIT_ISJ` / `MLIT_KSJ` と同じ体裁にする。

### 注意点

いずれも**試験公開**であり、「公開期間は公開終了まで」「URLやデータ構成、データの内容
(属性の有無や名称等)が変わる可能性があります」と明記されている。恒久的な依存先にはできない。
また将来 基本測量成果として提供される場合、承認が必要な位置づけに変わる可能性がある。

### タイルを元データとして使えるか

タイルは表示用に加工済みなので、原典の代わりにはならない。
PMTilesのメタデータに生成コマンドが残っており、tippecanoeで簡略化されていることが確認できる。

```
tippecanoe -P -f -q -pf -pk -S 2 -Z 14 -z 16 -B 14 -o output/tiles-25k.mbtiles
```

| | タイルから取る場合の劣化 |
| --- | --- |
| **注記(点)** | 座標がタイル内整数(4096分割)に量子化される。z16で約0.15m、z14で約0.6m。**実用上は問題にならない** |
| ライン・ポリゴン | `-S 2` で簡略化され、タイル境界で分割・重複する。**原典の代わりにはならない** |

つまり**名称(注記)が目的ならタイルで十分**で、形状の精度が要るなら元データに承認申請が要る。

> 地理院ベクトルタイルの課題を踏まえて、**設計改良を施したもの**です。

**提供実験版の `label` レイヤは漢字と読み仮名を対で持っている。** 最適化版には無い。

| --- | --- |

実際の値(東京駅付近 z14):

```

```

読み仮名は、かな入力での検索や表記ゆれの吸収に直接効く。**検索用途では提供実験版が有利**。

### 名称はすべて注記レイヤに集約されている

**両製品とも、名称は注記レイヤ(`label` / `Anno`)にしか無い。** 河川・建物・道路などの
ジオメトリ側には名前が付いていない。

| レイヤ (最適化版) | 地物数(全国) | 属性 |
| --- | ---: | --- |

## 4. PLATEAU の建物属性

`13103_minato-ku_pref_2025_citygml_1_op.zip` (2.0GB、展開後8.85GB / 57,278ファイル) で計測。
**zipは展開していない。** 中央ディレクトリから建物GMLのエントリだけを選び、
`unzip -p` で1本ずつストリーム展開して数えた (2.0GB / 51,170棟を約30秒)。

```sh

unzip -l "$ZIP" | awk 'NF>=4 && $1 ~ /^[0-9]+$/ && $4 ~ /udx\/bldg\/.*\.gml$/ {print $4}' > list.txt

# 選んだエントリだけをストリームして数える
while read -r f; do unzip -p "$ZIP" "$f"; done < list.txt \
| awk '/<bldg:Building /{b++} /<bldg:measuredHeight/{h++} /<bldg:usage/{u++} /<gml:name/{n++}
       END {printf "建物=%d height=%.1f%% usage=%.1f%% name=%.1f%%\n", b, 100*h/b, 100*u/b, 100*n/b}'
```

## 5. わかったこと

1. **PLATEAUは建物属性を完全に解決する。** 高さ・用途・階数が100%。Overtureの1.5% / 8.9%とは
   桁が違う。加えて耐火構造・用途地域・建蔽率・容積率まで揃っている
2. **ただし名前は無い (0.6%)。** 建物名で探す用途には使えない。
   Overture (13.6%) の方がまだ名前を持っている
3. **属性が構造化されているので、意味検索より素のSQLが適している。**
   `usage` も `districtsAndZonesType` もコードリスト値で、高さ・階数・建蔽率は数値。
   `WHERE measuredHeight > 60 AND usage = '454'` で足りる話に、埋め込みを持ち出す理由がない。
   意味検索が効くのは自由記述のテキストがある場合で、PLATEAUの建物はそれに当たらない
4. **地理院はタイルなら承認不要だが、元データ(基本測量成果)には第30条の承認が要る。**
   ただし手数料無料・約2週間なので、形状の精度が要るなら申請する価値はある
5. **名称が欲しいなら地理院の注記レイヤ。** 読み仮名まで欲しければ提供実験版。
   ただしジオメトリとは分離しているので、河川名・建物名にするには空間的な対応付けが要る
6. 注記は全国6,240万件。384次元float32の埋め込みを全件に持たせると約96GBで**非現実的**。
   意味検索に使うなら注記分類で絞るか、低ズーム(=重要度の高い)注記に限る必要がある

## 6. 属性フィルタと row group 枝刈りの関係 (実測)

PLATEAUの建物を高さで絞ったときに、転送量がどう変わるかを測った
(港区・ズーム16・7.3MBのファイルに対して)。

| 高さの下限 | 転送量 | 表示件数 |
| --- | ---: | ---: |
| 0m (絞らない) | 2,724 KB | 1,784件 |
| 60m以上 | **2,724 KB** (変わらない) | 27件 |
| 150m以上 | 1,970 KB (28%減) | 4件 |

**属性フィルタでは row group 枝刈りはほとんど効かない。** 理由は並べ替えの軸にある。
配信用の最適化 ([`spatial_pack`](../pipeline/src/spatial_pack.rs)) は行を**空間的に**
並べ替えるので、どの row group にも低い建物と高い建物が混ざる。
結果として全 row group の高さ統計が「0.6m〜200m前後」になり、
`height >= 60` では1つも枝刈りできない。

```
row_group  height min  max
0          1.5        172.7
1          0.8        235.0
2          0.6        224.6   ← どれも全域をまたぐ
3          0.6        211.5
4          1.2        332.1
5          3.0        212.4
```

150mでようやく減るのは、ページ単位の統計で一部が飛ばせるようになるため。

**枝刈りが効くのは空間フィルタ (bbox)。** 7.3MBのうち表示範囲分の2.7MBしか読んでおらず、
covering bbox による絞り込みはきちんと働いている。

したがって属性フィルタの利点は転送量ではなく、次の2つ:

1. **描画する地物が減る** (1,784件 → 27件)。ブラウザの描画負荷に効く
2. **2回目以降の絞り込みは通信ゼロ**。一度読んだ row group はDuckDB側にあるので、
   スライダーを動かしても再取得が起きない

数値属性で枝刈りを効かせたいなら、その属性を並べ替えの軸に含める必要がある
(ただし空間的な枝刈りとトレードオフになる)。

### 傾けたときの取得範囲

建物は `fill-extrusion` で立体に描いており、高さを持つ出所を選ぶと地図が傾く。
**傾けると `map.getBounds()` は地平線方向へ大きく広がる。**

| 傾き | 範囲の面積 | 読む量 |
| ---: | ---: | ---: |
| 0度 | 1.0倍 | 2,724 KB |
| 30度 | 1.5倍 | — |
| 50度 | 3.1倍 | **2,724 KB** (変わらない) |
| 60度 | 7.1倍 | 6,084 KB (2.2倍) |

範囲が3倍に広がっても読む量が変わらないのは、取得を**画面中心からの距離順**に
並べて上限で切っているため。遠景が落ちるだけで、新しい row group を読みに行かない。
60度まで倒すとさすがに増えるので、傾きは**50度**にしてある。

### 次の一手の候補

意味検索の材料を探す調査だったが、**見つかったのは「意味検索より構造化クエリが要る」という答え**だった。

- **PLATEAUで属性フィルタ付きの建物表示** — 以前アイデアとして出ていた
  「ドローン運用者向けに高さや用途で建物を絞る」がそのまま実現できる。
  意味検索も埋め込みモデルも要らず、今のGeoParquet + row group枝刈りの延長で成立する
- 意味検索を試すなら、自由記述テキストを持つデータ (施設の説明文など) を別途探す必要がある
