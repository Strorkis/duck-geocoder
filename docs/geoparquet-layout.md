# GeoParquet の並べ方と読み方 — 工夫・測った数字・見えていない課題

静的な置き場所 (R2) に置いた GeoParquet を、ブラウザの DuckDB-WASM が Range で部分的に読む。
そのために**ファイルの分け方・行の並べ方・行グループの切り方・読む側の問い合わせ**をどう決めたかを、
1か所にまとめる。経緯や細かい表は [pipeline.md](pipeline.md) にあり、ここからリンクする。

**この資料の目的は3つ。**

1. 工夫を、問い合わせの形 (点・画面・引いた画面・細長い範囲) との相性で整理する
2. **テストで見えていない部分**を書き出す。結果はデータの形 (密度・地物の大きさ・件数) で変わる
3. [Cloud Optimized GeoParquet (COGP)](https://github.com/Kanahiro/cloud-optimized-geoparquet) に
   返せそうな知見を、数字ごと残す

---

## 1. 前提: 何が速さを決めるか

### 配信元

R2 の公開URL (r2.dev) を手元から測った (2026-10-08)。

- **読み込み1回ごとに約0.45秒待たされる** (最初の1バイトが届くまで)
- **転送は約2MB/秒** (16Mbps)
- したがって **1回余計に読むのは、約0.9MB 余計に読むのと同じ重さ**

所要時間の見積もりは `0.45秒 × 回数 + 量 ÷ 2MB/秒`。手元の開発サーバーでは往復の待ちがほぼ0なので、
回数が増えても気付けない (下の「6. 再現の仕方」)。

### 読み手 (DuckDB-WASM)

| 性質 | 影響 | 出典 |
| --- | --- | --- |
| **1回ずつ順に読む** (並列にしない) | 回数がそのまま待ち時間になる。後から出した問い合わせは前の問い合わせの後ろで待つ | 計測 |
| 続けて読む間は読み取りを4倍ずつ伸ばす (16KB → 64KB → 256KB …)。**離れた場所を読むと16KBからやり直す** | 要るものを隣り合わせに置くと速い | pipeline.md「建物の並べ方」 |
| 一度読んだブロックは使い回す | 同じ範囲を2回問い合わせても、2回目はほぼ通信しない | 2026-10-10 に周辺検索で確認 |
| ファイルを開くたびに、HEAD (サイズ)・末尾・フッターで約3回 | **開くファイルの数**が効く | pipeline.md「建物の概観」 |
| 行グループの統計 (bbox 列の最小・最大) で読み飛ばす | **行グループ1つの広さ**が絞れる細かさの下限になる | 計測 |
| 開く往復は設定で1回にできる (`reliableHeadRequests: true` + `allowFullHTTPReads: false`) | 既定の2回 (GET bytes=0-0 → HEAD) が1回に | [duckdb-wasm-range-requests.md](duckdb-wasm-range-requests.md) |

**未確認のもの:** Parquet のページインデックスを読み飛ばしに使うか。範囲の条件を OR でつないだとき、
行グループの統計で読み飛ばすか。ブラウザの HTTP キャッシュが Range の応答をどこまで使い回すか。

### 結論: 決め手は3つ

1. **行グループ1つの大きさと広さ** — 量と、絞れる細かさを決める
2. **開くファイルの数** — 1ファイルにつき約3回の往復
3. **離れた場所を読む回数** — 要るものが散っていると、そのたびに往復

## 2. 使っている工夫

| 工夫 | 何をするか | 効いた場面 | 詳しく |
| --- | --- | --- | --- |
| **STR で並べて行グループに切る** | 行を空間的に並べ、行グループの bbox 統計を絞れるようにする | 逆ジオコーディング: 全国の行政区域 97.6MB から **1.5MB** | pipeline.md「4. 配信用に最適化する」 |
| **行グループの行数を1行の重さから決める** | 行の重さは3桁違う (行政区域 約43KB/行、点 約40バイト/行) ので、行数で固定しない | どのデータセットでも | 同上 |
| **bbox の列を先頭に置く** | DuckDB は範囲の条件に使う bbox を先に読む。後ろにあると読むたびに行グループの頭へ戻る | 東京タワー z16: 12.3MB・36回 → 8.7MB・20回 | pipeline.md「建物の並べ方」 |
| **線の粗い段 (足す)** | 路線ごとに統合・簡略化した行を同じファイルの先頭の行グループに**足す** (`lod = 0`)。引いた表示はそこだけ読む | 全国の高速道路 483KB、鉄道 329KB | pipeline.md「粗い段」 |
| **建物の段 (振り分け)** | 行を重要度の段 (公共施設 / 商業・業務 / 住宅・その他) に振り分け、段の境で行グループを切る | 東京駅 z13 の画面内の形: 全部なら約30MB、公共施設だけなら約2MB | pipeline.md「段で間引く」 |
| **場所ごとに区切り、場所の中を段で並べる** (CellFirst) | 約1MB ぶんの場所ごとに区切り、その中を段で並べる | 寄った表示: 段ごとの並べ方より読む量が半分以下 | pipeline.md「建物の並べ方」 |
| **概観 (別ファイルの複製)** | 最後の段を除いた行を、都道府県・QuadKey ごとに1ファイルへ集める | z13: **121秒 → 29秒** (R2 相当) | pipeline.md「建物の概観」 |
| **ファイルの分け方を件数で決める** | Overture の建物は QuadKey の適応的な四分木 (40万棟を超えたら割る)。PLATEAU は都市ごと | 1ファイルをメモリに載せて並べ替えられる大きさに | pipeline.md「建物を全国に」 |
| **カタログをファイル選びの索引にする** | Item の bbox で、画面に重なるファイルだけを渡す (`filesInView`) | 開くファイルを減らす | web/src/lib/sources.ts |
| **Item の一覧も GeoParquet に** (stac-geoparquet) | Collection ごとに行グループを分け、Item の少ない Collection をフッターの隣に置く | 起動時に要る行政区域の Item がフッターと同じブロックで読める | pipeline.md / stac_geoparquet.rs |

### 並べ方の比べ方 (repack の `Layout`)

| 並べ方 | 順序 | 合う問い合わせ | 使っているもの |
| --- | --- | --- | --- |
| `LevelFirst` | 段ごと → 段の中を場所で | 広い範囲の上の段だけを読む (引いた表示) | 線の粗い段 |
| `CellFirst` | 場所ごと → 場所の中を段で | 狭い範囲の全段を読む (寄った表示) | 建物の元のファイル |
| `Overview` | 段ごと → 場所で、別ファイル | 広い範囲の上の段だけを、少ないファイルで | 建物の概観 |

**段ごとと場所ごとはぶつかる。** 1つのファイルで両方を速くする並べ方は見つかっていない。
建物では「元のファイルは場所ごと + 引いた表示用に概観を複製」で両立させた (容量は約1割増える)。

## 3. 問い合わせの形ごとの相性

| 問い合わせ | 例 | いまの状態 (R2 相当) | 決め手 |
| --- | --- | --- | --- |
| **点** | 逆ジオコーディング | 速い (数回・1.5MB) | 行グループの広さ |
| **画面 (寄った表示)** | 建物 z16 | 28秒 (40回・4.8MB) | 開くファイルの数・場所ごとの並べ方 |
| **画面 (引いた表示)** | 建物 z13 | 29秒 (概観 3ファイル) | 開くファイルの数 → 概観 |
| **細長い範囲** | 路線の沿線 100m | **重い。** 東西線全体で約110秒の見積もり、前後1.5kmに絞って約80秒 | **行グループの広さ (都心で約2km四方)** |
| **全データを横断する集計** | 周辺検索 (8種類ほど) | 1分〜1分半 | データセットの数 × 開く回数 |

### 細長い範囲が苦手な理由 (2026-10-10 に測った)

東京駅 z14 の画面 (約4km × 2.5km) で、東西線の沿線 100m の建物を調べた。

- 都心の PLATEAU では、**行グループ1つ (約1MB) が約2km四方を覆う** (中央区: 5区画 × 3段)
- 画面全体に重なる行グループは48個。線に沿って500m四方の区画に分け、区画ごとに問い合わせても **34個**
  にしか減らない (統計から計算。区画は画面の半分を占めた)
- 押した地点の周り 1km に絞っても21個 (6.3MB)
- 周辺検索全体では、路線全体で 180回・48MB、前後1.5kmに絞って 142回・30MB

**行グループより細かい範囲は、問い合わせの書き方では絞れない。** 並べ方を細かくすると、
寄った表示で回数が増える (10-08 に「段ごと・256KB」で悪化を確認)。いまは機能の側で
「鉄道は押した地点の前後1.5kmだけを起点にする」とした (路線全体の沿線は重い問いとして扱う)。

### どこまでファイルを分けるか (未決)

**概観を作ると「1つの出所 = 1つのファイル」が崩れる** (利用者の指摘、2026-10-10)。
いまは建物だけで元のファイル 698個 + 概観 48個。分けるほど得るものと失うものがある。

| | 1ファイルに寄せる | 分ける |
| --- | --- | --- |
| 開く往復 | 1回 (フッターは大きくなる) | ファイルの数だけ (1つにつき約3回) |
| 範囲で絞る | 行グループの統計だけ | カタログの bbox でファイルごと飛ばせる |
| 作る・上げ直す | 全体を作り直す | 一部だけ作り直せる |
| 渡しやすさ | URL 1つで済む。COGP の考え方 (段を1ファイルの中に持つ) | カタログ (STAC) が無いと全体が分からない |
| メモリ | 並べ替えは全行をメモリに載せる (1棟約1.1KB) | 小さく分ければ載る |

- **フッターの大きさも開く重さになる。** 行グループが数百あるファイルではフッターが数百KBになり、
  1回で読み切れない。全国1ファイルにすると、この重さが効いてくるはず (未計測)
- 開く1回の重さは配信元で変わる (r2.dev は約0.45秒)。独自ドメインやキャッシュで軽くなるなら、
  分けたほうが有利な範囲は広がる
- 目安を出すには、同じデータを「全国1つ / 都道府県 / 都市」で作り、寄った表示・引いた表示・点の問い合わせで比べる

### 他の形式・他の手法 (未調査)

GeoParquet が合わないデータ・問い合わせには、別の形式を使う道もある。いまの記録は MLT の検討メモ
([roadmap.md](roadmap.md)「配信形式: MLT」) だけで、どれも自分のデータでは測っていない。

| 候補 | どんなものか (要確認) | 合いそうな場面 |
| --- | --- | --- |
| MLT (MapLibre Tiles) | 列指向のベクタタイル。MapLibre GL JS が読める | 引いた表示を**描く**こと (概観の役目をタイルが担う) |
| PMTiles | タイルを1ファイルにまとめ、Range で読む | 同上。地理院のベクトルタイルで既に参照している |
| FlatGeobuf | 地物ごとの空間索引 (packed Hilbert R-tree) を持つ | 行グループより細かい範囲の取り出し (細長い範囲) |
| GeoZarr | 多次元の配列 (格子) の形式 | 標高・人口メッシュ・時間で変わる格子 (気象など) |
| SedonaDB | Apache Sedona の単体で動く空間 SQL エンジン | 空間結合などの重い問い合わせ。ブラウザで動くかは未確認 |

## 4. テストで見えていない部分

E2E は**東京駅・東京タワー周辺 (都心・密)** と、**1280×720 の画面**で測っている。
結果はデータの形で変わるので、次のものは確かめていない。

| 見えていないもの | なぜ効くか | 確かめ方の案 |
| --- | --- | --- |
| **疎な地域** (地方都市・山間部) | 1MB の行グループが数十km四方になりうる。点の問い合わせでも広い範囲を読む | 前橋・地方の町で同じ計測 |
| **1件が巨大な地物** | 行グループの bbox 統計は外接矩形の和なので、1件の巨大な地物 (高架・河川敷など) が統計を引き伸ばし、読み飛ばしを効かなくする | 行グループごとに「統計の広さ」と「中身の99%の広さ」を比べる (下の SQL)。中央区では差は小さかった |
| **件数が少なく1件が重い面** | 行グループを細かく切れない (行政区域 1,741件) | COGP で段が消えた例 (pipeline.md) |
| **細長い・斜めの範囲** | 外接矩形が範囲の大半を空振りする | 上の「細長い範囲」 |
| **同時に複数の問い合わせ** | DuckDB-WASM は1本ずつ。地図を動かしながら周辺検索すると、後の問い合わせが待つ | 待ち行列の長さを数える |
| **r2.dev 以外の配信元** | 独自ドメインならキャッシュが効き、1回の重さが変わる。CDN の Range キャッシュの効き方も未計測 | 独自ドメインを付けたら同じ計測 |
| **端末と回線** | 1回の重さ・転送の速さ・メモリ (WASM は4GBまで) | — |
| **ページインデックス** | 使えれば行グループの中も読み飛ばせる。DuckDB-WASM が使うかは未確認 | 書き出しで付けて転送量を比べる |
| **古いアプリとの互換** | 並べ方やカタログを変えると、公開中の古いアプリが読む形とずれる | deploy.md の順序の注意 |

## 5. COGP に返せそうなこと

COGP の仕様 (2026-09-26 時点の SPEC.md) は、producer guidance で
「**粗→細の順に並べると、全体を1つの空間順に並べるより局所性が落ちることがある。
進んで描く用途と原寸の空間検索の両方を測るべき**」と書いている。ここでの測定はその実例になる。

| 候補 | 中身 | 手元の根拠 |
| --- | --- | --- |
| **段ごとと場所ごとの衝突を数字で示す** | 同じ建物データで、段ごと (COGP の形) と場所ごとを、寄った表示・引いた表示の両方で比べた表 | pipeline.md「建物の並べ方」の表 (z16 で 18MB・58回 → 4.4MB・30回) |
| **ファイルをまたいだ概観** | COGP は「1ファイルの中で各行を1度だけ」。開く回数が支配的な配信元では、**上の段だけを広い範囲で集めた別ファイル**が効く。STAC の Item で見分ける (`duck:lod_max`) | 概観で z13 121秒 → 29秒 |
| **線網の段は「足す」形** | 道路網では行を選ぶと網目が途切れ、行ごとの overview 列は行数の壁に当たる (国道 28.8万行で 4.7MB)。統合・簡略化した行を足す形を比べた | pipeline.md「COGP を手元のデータで測った」 |
| **件数が少ない面で段が消える** | `--min-root-features` の既定 (2048) を行政区域 (1,741件) が下回り、1 row group に退化 | 同上 |
| **読み手のコスト模型を guidance に** | 行グループの大きさは「1回の重さ ÷ 転送の速さ」で釣り合う (r2.dev で約0.9MB)。数字の目安を producer guidance に足せる | この資料の「1. 前提」 |
| **読み手の実装の課題** | DuckDB-WASM は順に読み、読み取りの伸ばし方が離れた場所でリセットされる。並べ方の評価は読み手に依存する | 同上 |
| **細長い範囲は行グループの広さに負ける** | 範囲の問い合わせの下限は行グループの広さ。ページインデックスの有無で変わるはず | この資料の「3」 |

**まだ言えないこと:** 地方・疎なデータでの結果、ページインデックスを使える読み手での結果、
r2.dev 以外の配信元での結果。返すなら、これらを測ってからのほうが説得力がある。

## 6. 再現の仕方

### R2 の遅さを手元で再現する

手元の配信 (vite の開発サーバー・preview) に待ちを足せる (web/vite.config.ts)。

```bash
DATA_LATENCY_MS=450 DATA_BANDWIDTH_MBPS=16 PLAYWRIGHT_TARGET=dist pnpm exec playwright test -g "周辺検索"
```

実際の R2 に向けるなら `VITE_DATA_BASE_URL` に公開URLを渡してビルドし直す (deploy.md)。

### 行グループの広さを調べる (DuckDB の CLI)

```sql
-- 行グループごとの bbox 統計の広さ (km) と大きさ
SELECT file_name, row_group_id,
  round((max(CASE WHEN path_in_schema = 'bbox, xmax' THEN stats_max_value::DOUBLE END)
       - max(CASE WHEN path_in_schema = 'bbox, xmin' THEN stats_min_value::DOUBLE END)) * 90, 2) AS width_km,
  round((max(CASE WHEN path_in_schema = 'bbox, ymax' THEN stats_max_value::DOUBLE END)
       - max(CASE WHEN path_in_schema = 'bbox, ymin' THEN stats_min_value::DOUBLE END)) * 111, 2) AS height_km,
  round(sum(total_compressed_size) / 1e3) AS kb
FROM parquet_metadata('data/output/plateau/plateau_bldg_13102.parquet')
GROUP BY ALL ORDER BY row_group_id;
```

範囲 (矩形) に重なる行グループの数と量は、上の統計を範囲と比べれば出る
(実際に読む量より少し少なく出る。フッターと、読み取りの伸ばし方の分が乗らない)。
